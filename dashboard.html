Data Quality Observations

All issues identified during EDA that drove the cleaning and harmonization decisions

  • ⚠️Inconsistent column names: 2017 uses dot-notation (Happiness.Score, Economy..GDP.per.Capita.); 2018–2019 use plain text (Score, GDP per capita)
  • ⚠️Inconsistent data types: Rank column is int64 named differently across years (Happiness Rank vs Overall rank). All numeric features are float64 — consistent internally but mapped to different concepts.
  • ⚠️Schema differences between years: Column count varies from 9 (2018–2019) to 13 (2016). Region only present in 2015–2016. Confidence intervals only in 2016, whisker values only in 2017.
  • ⚠️Family vs Social support: Same concept, renamed — harmonized to family
  • ✅1 missing value in 2018 Perceptions of corruption — filled with year-level median
  • ✅No duplicate records across any of the 5 source files
  • 🗑️Columns dropped: Dystopia Residual, Standard Error, Confidence Intervals (Lower/Upper), Whisker High/Low — year-specific or non-predictive

✓ Target Leakage — Avoided

Dropped in Step 2:
• Happiness Rank — derived 1:1 from happiness_score
• Dystopia Residual — encodes the WHR target score directly

All 8 selected features are independent inputs from the original survey, not computed from the target variable.

◎ Categorical Data — No Encoding Needed

region was explicitly excluded from the feature set.

Reason: Region is high-cardinality metadata used only for visualization (e.g., regional bar chart). Encoding it would introduce 10+ dummy variables that act as indirect proxies for GDP/health — adding noise, not signal. country and year are identifiers, not features.

◎ Normalization / Scaling — Not Applied

All 8 features are already on comparable WHR index scales (range ≈ 0–2, float64). Linear Regression does not require feature normalization when scales are similar — no regularization (Ridge/Lasso) is used, so there is no coefficient shrinkage bias from unscaled inputs. Random Forest is inherently scale-invariant. Scaling was evaluated and found unnecessary.

Why Linear Regression was chosen over Random Forest

Random Forest achieves better metrics (R²=0.785 vs 0.727, MAE=0.405 vs 0.449), but the workshop objective is pipeline integration, not model optimization (per rubric: "Use a simple regression model").

Additional technical justifications:
• Kafka consumer inference — Linear Regression produces a single deterministic predict() call; no ensemble aggregation, lower latency per event.
• Interpretability — coefficients directly show each feature's contribution to the happiness score prediction — easier to validate in a demo.
• Serialization — the model.pkl is ~1KB vs ~5MB for Random Forest, making it trivial to load on each Kafka consumer message.
• Sufficient accuracy — R²=0.727 explains 72.7% of variance, well above the threshold for a meaningful prediction pipeline.

Step 6 — Kafka Consumer

kafka/consumer.py · 7-step processing per message

  • 1 Receive message from Kafka topic
  • 2 Validate schema → determine status
  • 3 Store raw payload + status → raw_happiness_events + COMMIT
  • 4 Skip invalid events (continue) — pipeline never crashes
  • 5 Recompute engineered features in correct order
  • 6 model.predict(X) → predicted happiness score
  • 7 Store result → fact_predictions + COMMIT

Event Validation Logic — 4 Status Codes

Every event is validated before prediction. Invalid events are stored in the raw table with the appropriate status and then skipped — they never crash the pipeline.

StatusTrigger ConditionAction
VALID All required fields present, all numeric values are valid floats (not NaN/Inf) Stored + prediction generated
INVALID_SCHEMA One or more of REQUIRED_FIELDS missing from the JSON event Stored · skipped from prediction
INVALID_VALUES Numeric field cannot be cast to float, or value is NaN / Inf Stored · skipped from prediction
PREDICTION_ERROR Unhandled exception during feature engineering or model.predict() Status updated via UPDATE · pipeline continues
REQUIRED_FIELDS = {country, year, gdp,
 family, health, freedom, generosity, corruption}
NUMERIC_FIELDS = {gdp, family, health, freedom,
 generosity, corruption, year}

Consumer Write Flow — Transaction Boundaries

Two separate transactions guarantee raw event durability even if prediction fails.

TX 1 ─── validate event ───────────────────
    INSERT INTO raw_happiness_events (payload, status)
    COMMIT ← raw event persisted before prediction
TX 2 ─── valid events only ────────────────
    INSERT INTO dim_raw_event (parsed fields)
    model.predict(X) → predicted_score
    get_or_create_country / get_or_create_date
    INSERT INTO fact_predictions (scores, raw_event_id)
    COMMIT
ERR ─── on exception ─────────────────────
    ROLLBACK → UPDATE status = PREDICTION_ERROR
    pipeline continues (no crash)
